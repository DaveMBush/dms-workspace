# Story 7.1: Unit tests for yahoo-finance2 v4 upgrade contract

Status: ready-for-dev

## Story

As a developer,
I want a red-phase test that fails while `yahoo-finance2` is still on the v3 line and asserts (a) the declared version targets 4.0.4 and (b) consumer tests mock the `yahooFinance` instance module rather than importing the raw package,
So that Story 7.2 has an executable contract proving the upgrade to 4.0.4 landed with no test coupling to the package's internal implementation.

## Acceptance Criteria

1. A new unit test asserts the declared `yahoo-finance2` version in the root `package.json` satisfies `^4.0.4` (i.e., major version 4, specifically targeting 4.0.4) — it fails while the dependency is still on the v3 line (`^3.13.0`).
2. A test asserts that the server consumer specs do NOT import the raw `yahoo-finance2` package directly; they mock the instance module `apps/server/src/app/routes/settings/yahoo-finance.instance.ts` (the single re-export point), so the tests are insulated from v3→v4 internal API changes and can survive future package swaps.
3. All new assertions in this story are marked `.skip()` (`it.skip`) in code so CI stays green while the dependency is still on v3; every pre-existing test remains unskipped and green.

## Tasks / Subtasks

- [ ] Task 1: Add red-phase tests for the v4 upgrade contract (AC: #1, #2)
  - [ ] 1.1 In a new spec under `apps/server/src/` (e.g., `yahoo-finance2-version.spec.ts`), read the root `package.json` and assert the declared `yahoo-finance2` version satisfies `^4.0.4`.
  - [ ] 1.2 Add a test that inspects the consumer specs (`resolve-cusip.function.spec.ts`, `get-last-price.function.spec.ts`) and asserts they mock the instance module path (not an import of the raw `yahoo-finance2` specifier), so no test couples to package internals.
- [ ] Task 2: Mark all new tests `.skip()` so CI stays green (AC: #3)
  - [ ] 2.1 Prefix each new `it(...)` with `.skip` (`it.skip`) and add a comment noting Story 7.2 removes the skips, confirms red, then bumps the package until green.

## Dev Notes

- Red-phase TDD convention: this story writes failing tests marked `.skip()` in code (Vitest/Jest `it.skip`) so CI stays green; Story 7.2's FIRST task is to remove those skips, confirm they fail (red), then bump the package and fix breakage until green. Both stories are `Status: ready-for-dev`.
- **Current state verified on disk:** `yahoo-finance2` is declared in the ROOT `package.json` line 69 as `"^3.13.0"` (resolved to `3.15.4` in `pnpm-lock.yaml`) — it is NOT a key in `apps/server/package.json`. So AC #1 is genuinely red while on v3; that is the load-bearing failing assertion.
- **Single import point:** only `apps/server/src/app/routes/settings/yahoo-finance.instance.ts` (line 2) imports the raw package and re-exports the `yahooFinance` instance. All three consumers (`symbol/search/index.ts`, `import/resolve-cusip.function.ts`, `settings/common/get-last-price.function.ts`) call that instance, never the package directly — so AC #2's "mock the instance module" contract is already how the codebase is structured; this test just locks it in.
- **Why a version assertion:** the whole epic IS "bump to 4.0.4," so encoding that target as an executable test makes the red→green pair non-tautological (mirrors Epic 6's package.json-key pattern). Do NOT assert on `node_modules` or lockfile internals — read the declared root `package.json` value only, keeping the test fast and deterministic.
- **Prose note:** the epic prose says this "will need to be done in one story," but the validator forbids a single-story epic (count must satisfy both `% 2` and `% 3`). This is therefore the minimal valid pair: a red-phase contract + its implementation, with no e2e story.
