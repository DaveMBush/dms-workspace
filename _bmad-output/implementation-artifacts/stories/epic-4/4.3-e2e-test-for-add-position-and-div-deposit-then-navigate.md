# Story 4.3: E2E test for add-position / add-div-deposit then navigate

Status: in-progress

## Story

As a user (Dave),
I want an end-to-end proof that adding a position or dividend deposit and then navigating away does not crash the app,
so that I can trust both add flows in real use — including persistence of the added row.

## Acceptance Criteria

1. A new Playwright spec adds a position via the Add Position dialog on the Open Positions screen, navigates to Sold Positions (or Dividend Deposits), and captures zero `pageerror` events and zero `console.error` events for the whole flow; the target route renders its table normally.
2. The same spec (or a parallel test) adds a dividend deposit on the Dividend Deposits screen, navigates to Open Positions (or Sold Positions), and again captures zero `pageerror` / `console.error` events with the target route rendering normally.
3. After an add in either flow, the added row is visible with correct data (symbol, quantity, price, date for positions; date, amount, type for deposits) and survives a full page reload (`page.reload()` then re-assert) — server round-trip confirmed.
4. The existing e2e specs `open-positions.spec.ts` and `dividend-deposits-modal.spec.ts` pass unchanged alongside the new spec on chromium.

## Dev Notes

- **Prerequisite:** Story 4.2 must be complete (fix landed, unit tests green). This spec is the end-to-end proof of AC #3 from Epic 4; against unfixed code it will capture `pageerror`/`console.error` events on navigation after an add.
- **Error-event capture pattern:** in `beforeEach`, attach listeners to a fresh page: `page.on('pageerror', errors)` and `page.on('console', msg => { if (msg.type() === 'error') consoleErrors.push(msg.text()) })`; assert both arrays are empty at the end of each test. Asserting on browser console events in test code is fine — do NOT add any `console.*` to production source (`no-console` is a hard lint rule repo-wide).
- **e2e DB note:** run Playwright from workspace root (as the `@nx/playwright` executor does) so both server and helper hit `<root>/test-database.db`; regenerate with `node tools/create-test-db.js test-database.db` if seeding errors appear. The shared e2e SQLite DB accumulates rows across runs — kill orphaned servers + delete the DB for a clean run if count/filter assertions misbehave.
- **Reuse existing helpers:** follow the setup/teardown and dialog-driving patterns already used in `apps/dms-material-e2e/src/open-positions.spec.ts` (add-position flow) and `dividend-deposits-modal.spec.ts` (deposit flow) so the new spec stays consistent with the suite.
- Playwright for e2e; chromium project only is sufficient for this story.
