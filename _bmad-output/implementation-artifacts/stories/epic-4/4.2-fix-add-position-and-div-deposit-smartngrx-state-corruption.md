# Story 4.2: Fix add-position / add-div-deposit SmartNgRX virtual-array state corruption

Status: done

## Story

As a user (Dave),
I want adding a position or dividend deposit to not corrupt the in-memory `Account` entity's virtual-array state,
so that navigating away from the screen after an add does not throw an exception and my data is accurate and durable.

## Acceptance Criteria

1. No property is dropped or set to `undefined`.
2. After `DividendDepositsComponentService.addDivDeposit()` calls `divDepositsArray.add!(...)`, the parent `Account` entity's `divDeposits` field retains all three properties intact.
3. Story 4.1's red-phase unit assertions are unskipped and green under `nx test dms-material`, with no pre-existing test regressing.
4. The project lint + type-check/build pass with no new errors introduced by this story's changes.

## Dev Notes

- **Root cause (verified against installed smart-core):** SmartNgRX's `BaseArrayProxy.addToStore()` in `node_modules/@smarttools/smart-core/fesm2022/smarttools-smart-core.mjs` (~line 2141) reconstructs the parent virtual-array field as `{ indexes, length }` ONLY — it does NOT copy `startIndex`:

  ```js
  const existingVirtualArray = castTo(this.rawArray);
  const indexes = [...existingVirtualArray.rawArray];
  indexes[existingVirtualArray.length] = childId;
  castTo(newParent)[this.childDefinition.parentField] = { indexes, length: existingVirtualArray.length + 1 }; // startIndex dropped
  ```

  It then calls `parentService.loadByIdsSuccess([newParent])`. The later server-reconciliation step (`replaceIdInParents` → `processVirtualArrayChildField`) DOES spread the existing contents (preserving whatever is there), so once `startIndex` is dropped by `addToStore`, nothing restores it. Any subsequent read of the virtual array that depends on `startIndex` (e.g., re-evaluating a computed signal when the route changes) throws — matching Dave's "add then navigate away crashes" report.
- **Task 0 must confirm this empirically** before Task 1: unskip Story 4.1's tests and read exactly which field is `undefined`/corrupted post-add. The fix below assumes `startIndex` is the dropped property; if red shows a different/additional corruption, adjust accordingly.
- **The two add call sites** (both go through `SmartArray.add()` → `addToStore()`):
  - `apps/dms-material/src/app/account-panel/open-positions/add-position.service.ts:114` — `tradesArray.add!(tradeData, currentAccount())`.
  - `apps/dms-material/src/app/account-panel/dividend-deposits/dividend-deposits-component.service.ts:117` — `divDepositsArray.add!(...)`.
- **Virtual-array shape:** `{ startIndex: number; indexes: string[]; length: number }` (see `Account.openTrades` / `soldTrades` / `divDeposits` in `apps/dms-material/src/app/store/accounts/account.interface.ts`; default row factory in `accounts-definition.const.ts` seeds all three as `{ startIndex: 0, indexes: [], length: 0 }`).

### Fix options (pick the lowest correct layer; confirm via Task 0 first)

1. **Root-cause — update library reference**
This was fixed in `@smarttools/smart-core` version 4.0.1 (or later).
2. **App-level defensive repair** (fallback if a library patch is not acceptable): after each `.add!(...)` call, re-assert the parent's virtual-array `startIndex` through the store so it cannot be left `undefined`. More code, must cover both call sites, and races with the async reconciliation — use only if option 1 is blocked.
3. **Avoid the proxy `add()`** (last resort): manage the virtual array + child upsert manually in the service. Highest blast radius; only if 1 and 2 are both unsuitable.

- **Why not just "guard the read":** wrapping the computed-signal reads to tolerate a missing `startIndex` would hide the corruption instead of fixing it — the row count/index math would still be wrong. Fix the write path (Task 1), not the read path.
- **no-console is a hard lint rule** repo-wide (disable comments error). Do not add any `console.*` to production source in this story.
- Vitest for unit (`nx test dms-material`).
