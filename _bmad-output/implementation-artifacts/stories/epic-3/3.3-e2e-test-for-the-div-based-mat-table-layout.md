# Story 3.3: E2E test for the div-based mat-table layout

Status: in-progress

## Story

As a user,
I want the data tables to render and interact correctly after the **div-based** `mat-table` conversion (Story 3.2),
So that I can sort, select, scroll, and inline-edit in every table surface without regressions — with a fresh e2e spec proving the div-based layout works end-to-end, and the handful of consumer specs that still target native `<table>`/`<tr>`/`<td>` selectors updated to the new markup.

## Acceptance Criteria

1. A new spec `apps/dms-material-e2e/src/base-table-div-mat-table.spec.ts` asserts, on a seeded consumer screen (open-positions or global-universe), that the table renders as a **div-based** Material table: the `.mat-mdc-table` container is present inside the `cdk-virtual-scroll-viewport`, there is NO native `<table>` element inside the base-table host (`page.locator('dms-base-table table')` count is 0), body rows are `[role="row"].dms-body-row`, and header cells are `[role="columnheader"].dms-header-cell`.
2. The same spec asserts sticky-header behavior: while scrolling the `cdk-virtual-scroll-viewport`, the column-header row (`.dms-column-header-row`) stays pinned above the body — Material's native sticky headers now own pinning, so no manual two-region workaround is needed.
3. The same spec asserts sorting (clicking a sortable `.dms-header-cell[data-column=X]` toggles direction and shows the `[data-testid="sort-rank"]` badge when ranked), selection (select-all + per-row checkboxes toggle row state), and virtual scroll (scrolling renders additional rows without breaking layout) — reusing the existing seeder/helper patterns.
4. The consumer specs that still target **native-table** selectors are updated to div-based equivalents so they pass: `open-positions.spec.ts` (`td` → `.dms-body-cell[data-column=...]`), `symbol-filter-header.spec.ts` (`table tbody tr` → `[role="row"].dms-body-row`), `base-table-layout-regression.spec.ts` (all four native-tag selector constants — `tr.mat-mdc-header-row.dms-column-header-row`, `th.mat-mdc-header-cell[role="columnheader"]`, `tr.mat-mdc-row[role="row"]`, `td.mat-mdc-cell[role="cell"]` — plus the inline `td[role="cell"]` query in the alignment check and the DOM-tree doc comment → div-based equivalents), and `universe-table-workflows.spec.ts` (`tbody tr`, `td:first-child`, `td:nth-child(4)` → `[role="row"].dms-body-row` / `.dms-body-cell[data-column=...]`).
5. The ~50 consumer specs that target **class + ARIA-role** selectors (`.dms-header-cell[data-column=X]`, `.dms-body-row[role="row"]`, `.dms-body-cell[data-column=X]`) and the `dms-base-table` host selector pass UNCHANGED — they do not depend on the element being a native `<table>`.
6. The full e2e run (`pnpm nx run dms-material-e2e:e2e`) passes for all table-related specs: the new spec, the updated native-selector specs, and every surviving class/role-based consumer spec (including the already-repurposed "single-viewport mat-table regression" suites in `base-table-two-region-regression.spec.ts` and `base-table-layout-regression.spec.ts`).

## Dev Notes

- Cites AD-4 (single standard `mat-table` with native sticky headers replaces the two-region layout) from ARCHITECTURE-SPINE, and FR-2/FR-3/FR-4/FR-5/FR-7 (same as Epic 1). This is the e2e half of the triple for the div-based conversion; it depends on Story 3.2 being implemented first.
- **Why a new spec:** skipped Story 1.3 planned an e2e `base-table-mat-table.spec.ts` but was never run, so no e2e spec exists for the mat-table layout yet. This story creates the div-based one (`base-table-div-mat-table.spec.ts`). It is named distinctly from the (nonexistent) Epic 1 name to avoid confusion with the unit-test file of a similar name in `dms-material`.
- **Verified ARIA roles:** Material emits `role="row"` (rows) and `role="columnheader"` (header cells) via host bindings regardless of whether the host is a `<div>` or a native element. This is why the ~50 consumer specs that target `.dms-body-row[role="row"]` / `.dms-header-cell[role="columnheader"]` survive Story 3.2 untouched — they do not depend on the element being a `<table>`.
- **Verified selectors (Material 22.1.4):** both element and attribute forms are valid (`mat-table, table[mat-table]`, etc.), so the div-based form renders correctly; `.mat-mdc-table` is applied to the mat-table container in both forms and is a safe form-agnostic selector for "the table."
- **The two "two-region" regression specs were already repurposed during Epic 1** into "single-viewport mat-table regression" suites (their describe blocks read e.g. "Universe — single-viewport mat-table regression"). They use class/role selectors that survive the div-based conversion, so they are NOT deleted here — only `base-table-layout-regression.spec.ts`'s native `tr.mat-mdc-header-row` header selector needs updating (Task 2.3).
- **The `dms-base-table` host selector survives** in ~8 specs (`account-selection`, `sold-positions`, `lazy-loading-dividend-deposits`, etc.) — it targets the component element, not a native table, so no change is needed there.
- **e2e runtime:** `apps/dms-material-e2e/playwright.config.ts` uses `nxE2EPreset`, `workers: 1`, serial, shared SQLite. It boots (1) the Express API server on port 3001 (`DATABASE_URL=file:./test-database.db`) and (2) the Angular dev server on port 4301 with a proxy; `baseURL = http://localhost:4301`. Run via `pnpm nx run dms-material-e2e:e2e` (or the `e2e:dms-material:*` npm scripts). Git worktrees get a +100..+299 port offset.
- **Judgment call — scope of selector migration.** Only the four specs that target native `<table>`/`<tr>`/`<td>` elements are touched (Task 2). The ~50 class/role-based consumer specs and the `dms-base-table` host-selector specs pass unchanged. A broader cleanup (e.g. dropping legacy class aliases) is a separate follow-up, out of scope here to keep this single-session-sized.

### Project Structure Notes
