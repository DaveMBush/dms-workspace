## Epic 1: Table Layout Improvements

The core data surfaces (positions, dividends/deposits, global universe, screener) render through a single shared `dms-base-table` component. After this Epic, every table in the app renders with the standard Angular Material `mat-table` / `matColumnDef` / `mat-header-row` / `mat-row` syntax instead of the bespoke two-region DIV layout, and the header/table separation (which was only there to work around sticky-header scroll bugs) is removed. Users get the same 57px rows, virtual scroll, multi-column sort with rank badges, selection, and inline-edit cells — but built on the standard, more maintainable Material table primitives that were the original implementation.

**ADs covered:** AD-1, AD-2, AD-4
**FRs covered:** FR-2, FR-3, FR-4, FR-5, FR-7

### Story 1.1: Unit tests for the mat-table base-table conversion

As a developer,
I want a red-phase unit-test scaffold for the `dms-base-table` conversion to `mat-table`,
So that the implementation story has a defined, executable contract to make pass.

**Acceptance Criteria:**

**Given** the `dms-base-table` component is rendered in the Angular test harness
**When** the unit-test suite for `base-table.component.spec.ts` runs
**Then** it asserts the template emits `<mat-table>`, `<ng-container matColumnDef>`, `<mat-header-cell *matHeaderCellDef>`, and `<mat-cell *matCellDef>` markup
**And** it asserts the old two-region DIV markers (`.dms-table-header` / `.dms-outer-scroller` / `cdk-virtual-scroll-viewport` body) are no longer required for the header/body split
**And** it asserts sorting, selection, `renderedRangeChange`, and default cell rendering still behave as before

### Story 1.2: Convert dms-base-table to Angular Material mat-table

### Story 1.3: e2e test for the mat-table table layout

As a user,
I want the data tables to render and interact correctly after the conversion,
So that I can sort, select, scroll, and inline-edit in every table surface without regressions.

**Acceptance Criteria:**

**Given** the app is running and a table surface (e.g. open-positions or global-universe) is loaded
**When** the Playwright e2e suite drives the table

**And** the select-all checkbox and per-row checkboxes toggle selection
**And** vertical scrolling renders rows (virtual scroll) without breaking layout
**And** inline edit of a cell commits on Enter and cancels on Escape

## Epic 2: Remove Return of Capital

Return of Capital was previously modeled as a deposit type separate from Dividend, but the app only tracks total income generated by the investments regardless of its source. After this Epic, Return of Capital is no longer a distinct deposit type anywhere in the application — it is consolidated under Dividend — so the `divDepositTypes` seeding, the data-model documentation, and any residual handling are reduced to the canonical Dividend / Deposit type set. Users see one coherent income model with no stray "Return of Capital" option or record.

**ADs covered:** AD-7, AD-1
**FRs covered:** FR-5, FR-6, FR-7

### Story 2.1: Unit tests for removing Return of Capital

As a developer,
I want a red-phase unit-test scaffold asserting the `divDepositTypes` seeding no longer emits a "Return of Capital" type,
So that the implementation story has a defined contract to make pass.

**Acceptance Criteria:**

**Given** the Postgres seed routine `seedDivDepositTypes` in `scripts/seed-postgres.ts`
**When** the seed is executed against a clean database
**Then** the `divDepositType` rows seeded contain no "Return of Capital" entry
**And** the canonical server seed (`get-top-div-deposit-types.function.ts`) continues to seed exactly Dividend + Deposit

### Story 2.2: Remove Return of Capital handling

As a developer,
I want every separate handling of "Return of Capital" removed and consolidated under Dividend,
So that the app models a single income concept per the PRD glossary and AD-7.

**Acceptance Criteria:**
